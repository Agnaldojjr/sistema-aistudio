## 1. Observations

1. **R1 (3-Way Event Sync)**:
   - `CalendarView.tsx:91`: `window.addEventListener('appointments-updated', handleRefresh)` registers an event listener.
   - `DashboardView.tsx:456`: `window.addEventListener('appointments-updated', handleSync)` registers an event listener.
   - `DentalCRMView.tsx`: Does **not** contain any `window.addEventListener('appointments-updated', ...)` event listener. `DentalCRMView` dispatches events (lines 1962, 2698, 2895), but never listens for updates generated by `EventModal` or `DashboardView`.
   - `DashboardView.tsx:825`: Function `handleAssociatePatient` modifies appointment data and saves to Supabase CRM database, but **fails** to call `window.dispatchEvent(new Event('appointments-updated'))`.

2. **R2 (Financial Entry Unification & Deduplication)**:
   - `src/types.ts:167-179`: `PaymentRecord` interface defines standard fields: `{ id, patientId, patientName, date, amount, paymentMethod, status, description, appointmentId, procedureId }`.
   - `DashboardView.tsx:594-605`: `handleConfirmQuickPayment` creates objects matching `PaymentRecord` with `amount`, `paymentMethod`, `status: 'Pago'`, `appointmentId`, `procedureId`.
   - `FinancialView.tsx:57, 72, 195`: Reads `p.amount`, `p.paymentMethod`, and `p.status === 'Pago'`.
   - `DentalCRMView.tsx:373, 1131`: `localList` payments are created with non-standard properties: `{ id, patientId, date, method, description, value }` (using `method` instead of `paymentMethod`, `value` instead of `amount`, and missing `status`).
   - `DentalCRMView.tsx:5289, 5322, 5327`: Reads `pay.value` and `pay.method`. When processing `PaymentRecord` objects created from `DashboardView` (which have `amount` and `paymentMethod`), `pay.value` evaluates to `undefined` (displaying R$ 0,00) and `pay.method` evaluates to `undefined` (falling back to "PIX").
   - `DashboardView.tsx:589`: Procedure payment IDs are generated as `pay-proc-${appt.linkedProcedureId}` with `procedureId: appt.linkedProcedureId`.
   - `DentalCRMView.tsx:1126`: Procedure payment IDs are generated as `pay-${instanceId}` without setting `procedureId`.
   - `FinancialView.tsx:42-46`: Deduplication key calculation uses `p.procedureId ? proc:${p.procedureId} : ...`. Payments generated by `DentalCRMView` lack `procedureId`, resulting in separate keys and **failing to deduplicate** with `DashboardView` entries.

3. **R3 (Daily Summary Card Counter Accuracy)**:
   - `DashboardView.tsx:1064-1085`:
     - `Total Consultas`: `appointments.length`
     - `Confirmadas`: `appointments.filter(a => a.status === 'Confirmado').length`
     - `Faltas`: `appointments.filter(a => a.status === 'Falta' || a.status === 'Faltou').length`
     - `Pendentes`: `appointments.filter(a => a.status === 'Pendente' || a.status === 'Agendado' || a.status === 'Reagendado').length`
   - Appointments with status `'Atendido'` (set when quick payment completes) are omitted from `Confirmadas`, `Faltas`, and `Pendentes`. Consequently, `Confirmadas + Faltas + Pendentes != Total Consultas` when any attended appointments exist.
   - `DashboardView.tsx:394`: Revenue estimation uses `parseFloat(valMatch[1].replace('.', '').replace(',', '.'))`. Standard English formatted numbers like `500.00` in descriptions are parsed as `50000` ($50,000 instead of $500.00).

4. **R4 (tsconfig & Test Script Setup)**:
   - `tsconfig.json:26`: Includes `"src/**/*"` and `"server.ts"`, but excludes `"tests/**/*"`.
   - Workspace root: No `playwright.config.ts` or `playwright.config.js` exists.
   - `tests/regressions.test.ts:3` and `tests/ux_flow.test.ts:3`: `BASE_URL` points to remote Vercel environment `https://sistema-aistudio.vercel.app/?bypass_auth=true`. `npm test` does not start or test local workspace code changes.
   - `tsc --noEmit` passes with 0 errors for `src/**/*` and `server.ts`.

## 2. Logic Chain

1. **R1**: For true 3-way synchronization, all three view modules (`DashboardView`, `CalendarView`, `DentalCRMView`) must both dispatch and subscribe to the `appointments-updated` window event. Since `DentalCRMView` does not listen for `appointments-updated`, any appointment created or modified in `EventModal` or `DashboardView` remains stale in `DentalCRMView`. Additionally, because `handleAssociatePatient` in `DashboardView` skips dispatching the event, updates to patient assignment are not broadcast.
2. **R2**: Financial entry unification requires a single, consistent data schema (`PaymentRecord`) across all views. `DentalCRMView` writes `{ value, method }` while `DashboardView` and `FinancialView` write and read `{ amount, paymentMethod, status }`. This property mismatch causes `FinancialView` to calculate `NaN` or 0 for `DentalCRMView` entries, while `DentalCRMView` displays `R$ 0,00` for `DashboardView` entries. Furthermore, inconsistent ID prefixing (`pay-proc-` vs `pay-`) breaks the Map deduplication in `FinancialView`, producing duplicate financial rows.
3. **R3**: Summary cards in `DashboardView` present status breakdowns (`Confirmadas`, `Faltas`, `Pendentes`). When appointments transition to `'Atendido'`, they are excluded from all three sub-counters while remaining in `Total Consultas`, causing a discrepancy between the total counter and the sub-counters.
4. **R4**: Test infrastructure must validate local code changes. Missing `"tests/**/*"` in `tsconfig.json` excludes test files from static type checking. Missing `playwright.config.ts` and hardcoding a remote Vercel URL in test files causes `npm test` to test a distant pre-deployed site rather than local code modifications, violating test isolation and verification requirements.

## 3. Caveats

- Playwright tests could not be run locally against the hardcoded Vercel URL during review because the execution environment operates under `CODE_ONLY` network isolation (preventing outbound internet access).
- No production database corruption was observed during static type checking (`tsc --noEmit` passed for `src/`).

---

## 4. Conclusion

The implementation of R1, R2, R3, and R4 is incomplete and contains critical design flaws:
- **R1**: Incomplete event bus listener coverage in `DentalCRMView` and missing dispatch in `handleAssociatePatient`.
- **R2**: Schema fragmentation (`value`/`method` vs `amount`/`paymentMethod`) and broken deduplication keys (`pay-proc-` vs `pay-`).
- **R3**: Counter mathematical mismatch due to unhandled `'Atendido'` status.
- **R4**: Missing `tests/` in `tsconfig.json`, missing `playwright.config.ts`, and test files targeting external URLs rather than local code.

## Adversarial Challenge Report

### Overall Risk Assessment: HIGH

### Challenges

1. **Challenge 1: Financial Schema Fragmentation (Critical)**
   - *Attack Scenario*: User marks procedure as executed in `DentalCRMView`. System creates payment with `{ value: 250, method: 'PIX' }`. User opens `FinancialView`.
   - *Result*: `FinancialView` reads `p.amount` (undefined) and `p.status` (undefined). Revenue stays R$ 0,00. User opens `DentalCRMView` after paying in `DashboardView` (`amount: 250`). `DentalCRMView` displays `pay.value` (undefined) as `R$ 0,00`.
   - *Mitigation*: Unify all payment creation to use the `PaymentRecord` interface (`amount`, `paymentMethod`, `status`).

2. **Challenge 2: Event Bus Blind Spot in CRM (Major)**
   - *Attack Scenario*: Doctor creates/edits appointment in `EventModal` while `DentalCRMView` is open in another tab/panel.
   - *Result*: `DentalCRMView` never receives `appointments-updated` event. Doctor sees outdated appointment status until hard page refresh.
   - *Mitigation*: Add `appointments-updated` listener in `DentalCRMView.tsx`.

3. **Challenge 3: Counter Math Drift (Medium)**
   - *Attack Scenario*: Clinic marks 3 appointments as "Atendido".
   - *Result*: `Total Consultas` = 3, `Confirmadas` = 0, `Faltas` = 0, `Pendentes` = 0. Dashboard displays 3 total appointments but zero sub-counter entries.
   - *Mitigation*: Include `'Atendido'` in an explicit `Atendidas` counter or group with `Confirmadas`.

4. **Challenge 4: Self-Certifying Remote Tests (Major / Integrity)**
   - *Attack Scenario*: Developer modifies local business logic in `DashboardView.tsx` and runs `npm test`.
   - *Result*: `npm test` executes Playwright tests against `https://sistema-aistudio.vercel.app` (the live production server), ignoring all local code changes completely. Tests pass even if local code is broken.
   - *Mitigation*: Add `playwright.config.ts` targeting `http://localhost:5173` with local dev server launch.
